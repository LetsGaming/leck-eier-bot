# Seam Performance, Scalability & Storage Review — 2026-09-05

Scope: the boundary between `src/` (bot) and `web/src` + `src/web/**` (dashboard) — specifically whether their performance/storage characteristics interact. Read-only, no changes made.

## Summary

The single most important seam fact — **not stated explicitly in either prior report** — is that the bot and the dashboard are **the same Node.js process, sharing one `better-sqlite3` connection object** (`export const db = new Database(DB_PATH)` in `src/db/index.ts:25`, imported everywhere, in both `src/` and `src/web/**`; confirmed by `package.json`'s single `"start": "node dist/index.js"` entrypoint, `Dockerfile`'s single `CMD`, and `src/index.ts` calling `startWebServer(client, config)` in-process). This overturns the framing — though not entirely the conclusion — of the bot report's biggest concurrency finding (missing `busy_timeout`): there is no second OS process independently racing writes against the file, so `SQLITE_BUSY` from *internal* self-contention is not actually reachable the way that report describes. What the two halves genuinely share is a **single Node.js event loop and main thread**: because `better-sqlite3` is fully synchronous, a long-running dashboard query (the unbounded `member_records` scans both reports separately flagged) doesn't just slow that one HTTP response — it blocks Discord gateway processing (heartbeats, message/voice events) for its entire duration, for every concurrent user of the bot, not just the admin waiting on the dashboard. That's the real cross-half risk this codebase has, and it's more serious in combination than either report captured alone, even though today's data volumes keep it firmly sub-millisecond. Everything else at the seam — settings cache invalidation, boot-time member seeding, and the voice-log growth path — turns out to be either already handled correctly (an existing `settingsBus` pattern proves the seam-safe cache the bot report suggested would just work) or a non-issue (no code path was found where bot-side reads hit the same unbounded tables as the dashboard, and the voice log is never read back in bulk by the dashboard).

## 1. Concurrent write contention on the single SQLite file

**Reframed, not dismissed.** Single process + single connection means better-sqlite3 calls run to completion synchronously before the next line of JS executes — there is no way for two `.run()` calls issued by this application to literally overlap in time. The scenario the bot report describes ("a dashboard admin editing settings at the exact moment the bot's Apollo sweep... lands") cannot produce `SQLITE_BUSY` from internal contention, because the two writes can never be "at the exact moment" of each other inside one thread.

What *can* still happen, and is worth naming precisely:
- **`busy_timeout` still has no real trigger in this deployment.** No backup tool, `litestream`, or `sqlite3` CLI script exists anywhere in the repo (`scripts/`, `docs/`) that would open a second connection to `bot.sqlite` while the app runs. The only realistic way to hit `SQLITE_BUSY` today is an operator manually opening the file with an external `sqlite3` client for inspection while the bot is live — a real but rare, manual scenario, not an every-request one. **Verdict: still a one-line, zero-risk fix worth doing (defense in depth for any future second writer — e.g. a maintenance script, a future horizontally-scaled deployment, or WAL-mode readers during a checkpoint), but its priority should drop from "will bite occasionally under concurrent load" (bot report) to "cheap insurance against a scenario that doesn't currently exist."**
- **Multi-statement writes that `await` a Discord REST call in between DB statements are a real (if low-severity) interleaving risk — but a logical-ordering one, not a lock-contention one.** E.g. `src/web/routes/reactionRolePanels.ts`'s PATCH/mapping routes call a DB write, then `await trySync(...)` (a Discord REST round-trip), during which the event loop is free to run a bot-side handler (e.g. a member clicking the same panel via `reactionRoleEvents.ts`) against the just-committed row. Because each individual DB statement still commits atomically and the reaction-role read path (`getPanel`/`panelCache`) always re-reads current state, this cannot corrupt data — at worst a click during a multi-step edit sees an intermediate config state for one panel. **Ranking: theoretical, no realistic user-visible impact for a single-guild admin dashboard with one editor at a time.**
- **`removeRegistration()`/`clearRegistrationOnLeave()`** (`src/events/registerWatcher.ts:253-269`) follow the same await-REST-then-write-DB shape and are called from both the dashboard's `DELETE /members/registrations/:userId` and the bot's `guildMemberRemove` handler — again no corruption risk, just an ordering nuance if a member happens to leave the instant an admin removes their registration. Not worth guarding against at this scale.

**Bottom line for area 1: add `busy_timeout` (cheap, correct hygiene), but the two prior reports' implicit "two processes racing" mental model does not match this codebase's actual deployment — worth documenting so a future contributor doesn't over-invest in cross-process locking strategies (e.g. `WAL` checkpoint tuning, connection pooling) that solve a problem this app doesn't have as currently shipped.**

## 2. Duplicated/uncached reads of the same growing data from both sides

Checked whether the bot side ever calls `listAllMemberRecords()` or `listRegistrations()` (the two functions the dashboard report flagged as unbounded full-table scans): **it does not.** Grepping all of `src/` (excluding `src/web`) for both symbols returns zero call sites outside `src/web/routes/memberAudit.ts` and `src/web/routes/registrations.ts`. So there is no scenario where a bot-side hot-path read and the dashboard's unbounded scan are contending *for query cost* on the same table — the dashboard is the only reader of the full-table shape.

**However, the real seam risk here isn't query contention, it's event-loop contention** (see Summary): because both halves run on one thread, `listAllMemberRecords()` + `matchesSearch()`/`scoreMatch()`'s per-candidate Unicode transliteration (`src/services/memberSearch.ts:26-36`) running synchronously **is not just a slow HTTP response** — for its full duration, the bot cannot process any Discord gateway packets, including heartbeats. At today's `member_records` size (low hundreds to low thousands of rows) this is sub-millisecond and irrelevant. It becomes a genuine risk only if that table grows into the tens of thousands of rows *and* an admin searches Member Audit during a moment gateway responsiveness matters (e.g. a heartbeat ack window) — a combination this bot's scale won't reach for years, but one neither prior report's framing ("slow response" vs. "grows with account age") makes explicit as a *gateway-blocking* risk rather than a purely dashboard-side one.

**Ranking: theoretical today (both prior reports already correctly judged the query itself as fine for years); the added seam-specific nuance — that this cost is paid by the whole bot process, not just the requesting admin's browser tab — is worth recording as the reason to eventually act on the dashboard report's pagination/SQL-filtering suggestion, if event-loop-sensitive symptoms (e.g. occasional gateway reconnects) are ever observed.**

## 3. Whether bot-side writes create dashboard-side scaling problems downstream, or vice versa

- **`apollo_event_voice_log` → dashboard read-back: no compounding found.** The dashboard never reads the raw voice log in bulk. The only consumers are `listVoiceLogForUser(eventId, userId)` (bounded per-signup, already correctly identified as a small, capped N+1 by both prior reports) and `listVoiceLog(eventId)` (`src/services/eventAttendance.ts:230`, used only by `catchUpApolloEvents()` on bot restart, bounded to one event's rows). No web route or `web/src` component was found reading the full table or a full per-event log for display. **The hypothesis in the task brief (that `EventAttendanceDetail` might display the voice log in a way that scales with the unbounded table) does not hold — `EventAttendanceDetail.tsx` only ever shows derived attendance status, not raw log entries.** This is good news: the bot report's flagged unbounded-growth table does not have a matching unbounded-read on the dashboard side, so its growth risk stays exactly what the bot report already said (slow-burn, storage-only, not compounded by dashboard query cost).
- **`seedMemberRecordsFromCache()` boot loop vs. a dashboard request arriving mid-boot: not possible, by construction.** `src/index.ts`'s `clientReady` handler runs strictly sequentially: `initMemberCache()` → `seedMemberRecordsFromCache()` (synchronous, un-transacted loop) → `syncAnchorMessage()` → `syncAllPanels()` → **only then** `startWebServer(client, config)` (`src/index.ts:207-227`). Fastify does not start listening until after the seeding loop has fully completed. **There is no window in which a dashboard HTTP request can arrive while `seedMemberRecordsFromCache()` is running — the port isn't open yet.** This refines (in the "good news" direction) the bot report's §5.2 finding: the un-transacted loop is worth fixing for startup-time reasons (still a valid, cheap fix), but it carries zero seam risk, contrary to what the task brief hypothesized.

**Ranking for area 3: no real cross-half interaction found in either direction — this is the one section where investigation reduced risk rather than found new risk.**

## 4. Settings/config re-read cost across the boundary

- **The `settings` row does not grow.** Every column in `src/db/settingsRepository.ts`'s schema is a fixed-size scalar (booleans, nullable IDs, and a handful of template strings/`font_map`, all bounded by validation — e.g. `isValidFontMap()` requires exactly 52 characters). There is no JSON blob or unbounded text column on this row, so `getSettings()`'s per-message cost (bot report §1.2) will not get more expensive over time regardless of how many times the dashboard writes to it — the dashboard-save path (`src/web/routes/generalSettings.ts`) always does a full-row `UPDATE`, never an append.
- **A `settingsBus`-invalidated in-memory cache would be seam-safe with no gotcha — and this is already proven in production, not just theoretically sound.** `updateSettings()`/`setCommandOverride()` (`src/db/settingsRepository.ts:150,192`) both call `settingsBus.emit(...)` unconditionally, regardless of whether the caller was a slash command or a dashboard route — `src/web/routes/generalSettings.ts`'s `PATCH /settings/general` calls the exact same `updateSettings()` function the bot itself would call, so there is no separate write path to keep in sync. Better still, this exact pattern already exists and is exercised across the seam today: `src/services/reactionRoles.ts:43-60`'s `panelCache` is invalidated via `settingsBus.on(SettingsEvent.ReactionRoles, ...)`, and every mutating function in `src/db/reactionRolesRepository.ts` (all 8 write paths, called from `src/web/routes/reactionRolePanels.ts`) emits that event. Because bot and dashboard share one process and one `EventEmitter` instance, there is no cross-process pub/sub problem to solve (no Redis/IPC needed) — a bare `EventEmitter` is sufficient and already correctly wired. **This directly validates the bot report's suggested fix for §1.2 (cache `getSettings()`, invalidate via `settingsBus`) as low-risk and pattern-consistent with what's already shipped**, contradicting any assumption that seam-awareness would require extra plumbing.

**Ranking: no risk found; if anything this section produced a positive finding — the suggested fix from the bot report is a known-good, already-proven pattern in this codebase, not a new integration risk.**

## 5. Consistency/contradiction check between the two reports

- **No direct contradictions found.** Both reports independently reached compatible conclusions on the tables they both touched (`apollo_event_voice_log`: bot report calls it the single biggest unbounded-growth table; dashboard report ranks it below `member_records` — these are consistent, just weighted by each report's own scope). Both correctly identified `member_records`/`apollo_event_signups`-adjacent tables as growing with unique-humans/events rather than raw activity volume.
- **Both implicitly assumed a multi-process deployment for the `busy_timeout` finding** (bot report explicitly; the dashboard report doesn't address concurrency at all beyond "WAL mode is the right call for a server that's both reading and writing concurrently," which is true but doesn't distinguish between two threads-in-one-process vs. two processes). Neither report verified there is only one `new Database(...)` call in the codebase — this seam-level check is the one piece of due diligence that changes the practical risk assessment (see area 1).
- **No table was found where *both* halves independently do unbounded reads or writes on the same data** — the closest candidate (`member_records`) is written by the bot (`upsertJoin`/`updateProfile`/`recordLeave`, all single-row, indexed-by-`user_id` writes) but only *read in bulk* by the dashboard; the bot never bulk-reads it. So the risk stays additive-by-half rather than doubled, contrary to what the task brief flagged as a possibility to check for.
- **Neither report weighed the shared-event-loop consequence of the dashboard's unbounded scans** (area 2 above) — each treated it purely within its own half's terms (bot report: "any future slow query... translates to gateway latency" as a generic caveat; dashboard report: "per-request cost and memory grow... linearly and permanently" as a dashboard-response-time framing). Put together, the dashboard's own already-flagged worst finding (`GET /members/audit`'s unbounded scan) is the *same* risk the bot report's §1.1 caveat was warning about in the abstract — this is the one place where reading both reports side-by-side surfaces something neither states on its own.

## Priority Recap (seam-specific)

**Will bite within realistic growth (low-moderate severity, worth planning for):**
1. §2 — `GET /members/audit`'s unbounded scan is not just a slow dashboard response as `member_records` grows into the tens of thousands of rows; it's a synchronous block of the entire bot process's event loop (gateway heartbeats included) for its duration, because bot and dashboard share one thread. This raises the effective priority of the dashboard report's existing #1 finding (paginate/push search into SQL) — the impact isn't confined to the dashboard tab, it's shared with live Discord traffic.

**Cheap, no-downside, worth doing regardless of the reframing:**
2. §1 — add `busy_timeout` pragma to `src/db/index.ts`. Still correct defense-in-depth (guards against a future second writer — a maintenance script, a horizontally-scaled deployment, or manual `sqlite3` CLI inspection) even though the "two processes racing" scenario as originally described isn't reachable today.
3. §4 — implement the bot report's suggested `getSettings()` in-memory cache invalidated via `settingsBus`; this seam review confirms the exact pattern is already proven safe and correct via `reactionRoles.ts`'s `panelCache`, so there's no seam-specific risk to weigh against the cheap perf win.

**Theoretical / no action needed — investigation reduced rather than raised risk:**
4. §3 — `apollo_event_voice_log` growth does not compound with any dashboard read (no bulk voice-log read-back exists), and `seedMemberRecordsFromCache()`'s un-transacted boot loop cannot collide with a dashboard request (the web server isn't listening yet during that window). Both remain worth fixing for the reasons the bot report already gave (storage hygiene, startup time), just not for seam reasons.
5. §1 — multi-statement writes that `await` a Discord REST call mid-transaction (reaction-role panel edits, registration removal) can theoretically interleave with a concurrent bot-side handler, but at worst this is a benign ordering nuance (an intermediate config state briefly visible), not data corruption, at this bot's single-admin-at-a-time usage pattern.

**Cross-report correction:**
6. Both reports' `busy_timeout` and general concurrency framing implicitly (bot report explicitly) assumed two independent OS processes/connections sharing the SQLite file. There is only one process and one connection (`src/db/index.ts:25`, confirmed via `package.json`, `Dockerfile`, and `src/index.ts`'s call graph). This doesn't invalidate the fix, but it changes *why* it matters and should be corrected in institutional memory so a future reader doesn't design around a multi-process contention model this deployment doesn't have.
