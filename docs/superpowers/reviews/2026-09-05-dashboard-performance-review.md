# Dashboard Performance, Scalability & Storage Review

**Scope:** `web/src/**` (React/Vite dashboard) and `src/web/**` (Fastify routes/auth/session), with `src/db/**` read only to check what the dashboard's queries cost. Read-only audit, no changes made. Date: 2026-09-05.

## Summary

The event-attendance path (`src/db/eventAttendanceRepository.ts`, `src/web/routes/eventAttendance.ts`) is genuinely well-engineered for scale: batched `GROUP BY` summaries instead of N+1, a deliberately-added `starts_at` index, month-scoped queries pushed into SQL, and capped "all months"/"problems" list modes. The frontend has no polling, a tiny dependency footprint, and reasonable debouncing. The real risk in this codebase is **storage/memory growth on the member-history side**: `GET /members/audit` and `GET /members/registrations` both load the *entire* `member_records` table (every member ever seen, including everyone who has left, for the life of the bot) into Node memory and filter/sort/search it in JavaScript on every keystroke, with no time-based retention anywhere in the schema. For a single guild this is fine today, but former-member and registration-history rows never get pruned, so per-request cost and memory grow linearly and permanently with account age — the biggest "will bite in a year or two" item, not any single algorithmic hotspot. `apollo_event_voice_log` (the second-biggest un-pruned table) grows more slowly and is lower priority.

## Query / N+1 patterns

1. **Low impact (bounded, will not bite):** `recomputeAttendanceForEvent()` (`src/services/eventAttendance.ts:125-140`), triggered by the dashboard's `PATCH /events/attendance/signups/:signupId` route, issues one `listVoiceLogForUser` query per trackable signup on the event rather than one batched query. This is a per-event N+1, but N is bounded by attendee count for a single event (tens, not thousands), so it's cheap regardless of how much history accumulates. Not worth changing.
2. **Theoretical, no real fix needed:** `eventAttendance.ts`'s `serializeSignup()` (`src/web/routes/eventAttendance.ts:135-172`) calls `listVoiceLogForUser` again per signup when serializing an *active* event's list — same bounded-by-attendee-count situation, and at most one event is ever active at a time (enforced by the domain, documented in code). No action needed.
3. **Everything else in `eventAttendanceRepository.ts` is already correctly batched** — `summarizeSignupsForEvents()` uses one `GROUP BY` query for N events instead of N queries (the file's own comments note this replaced an earlier N+1 implementation). Good prior art; no further action.

## Missing indexes

No missing indexes were found for what the dashboard actually queries. `idx_apollo_events_starts_at`, `idx_apollo_events_status_starts`, `idx_apollo_signups_event`/`_user`, and `idx_apollo_voice_log_event` all exist and match the shapes of `listEventsInRange`/`listEventsAllMonths`/`listEventsWithUnresolvedSignups`/`listVoiceLogForUser`. The `LOWER(title) LIKE '%x%'` event-title search is a leading-wildcard scan that no B-tree index could serve anyway — this is called out explicitly in a migration comment (`src/db/index.ts:636-642`), and is a reasonable tradeoff at this scale (hundreds of events, not millions).

One soft gap: `member_records.register_status` has no index (`src/db/memberRecordsRepository.ts:52`, `selectRegistrationsStmt` filters `WHERE register_status IS NOT NULL`), but the table is one row per user *ever seen*, which for a single-guild bot stays in the thousands at most — a full scan here is not a real cost. **Theoretical, low real-world impact.**

## Unbounded response payloads

1. **Will bite within realistic growth (highest priority finding):** `GET /members/audit` (`src/web/routes/memberAudit.ts:36-100`) calls `listAllMemberRecords()` (`src/db/memberRecordsRepository.ts:98-100`), which is `SELECT * FROM member_records` with **no WHERE, no LIMIT** — every member ever seen, joined or left, for the entire lifetime of the bot. This runs on *every keystroke* in the Member Audit search box (300ms debounced) and also on every load of `EventAttendanceDetail.tsx` (which calls `api.memberAudit("")` just to get the in-guild list for its member-linking picker — see `web/src/pages/EventAttendanceDetail.tsx:38-43`). The in-guild list is separately capped by `FIND_USER_LIST_LIMIT` (500) and the left-list by `MEMBER_AUDIT_LEFT_LIMIT` (500) *after* filtering, but the initial DB read and the `matchesSearch`/`scoreMatch` pass (which does Unicode normalization + transliteration per candidate, see `src/services/memberSearch.ts:26-36`) runs over the **full unfiltered table** every time. For an active Discord community running for a few years, cumulative left-members alone could be in the low thousands; this scan is currently sub-millisecond-to-low-millisecond territory but is the one query in this codebase whose cost grows without bound as the guild's join/leave history accumulates, with zero retention policy anywhere to cap it. Suggested direction: push the `q` filter into SQL (a simple `LIKE`/normalized-column search) with `LIMIT`/`OFFSET`, or at minimum stop calling the full member-audit endpoint from `EventAttendanceDetail.tsx` just to populate a linking dropdown — a dedicated lightweight "in-guild members only" endpoint would avoid loading the `left` half of the table entirely for that use case.
2. **Will bite within realistic growth:** `GET /members/registrations` (`src/web/routes/registrations.ts:32-81`) calls `listRegistrations()`, which is `SELECT * FROM member_records WHERE register_status IS NOT NULL ORDER BY register_submitted_at DESC` with **no LIMIT** — every registration form ever submitted (pending/registered/removed/left), by design shown as full history. Every member who ever registers adds a permanent row here; there's no cap, and filtering/scoring (again via `matchesSearch`/`scoreMatch`, including transliteration) happens in JS over the full unfiltered result set on every request. Lower urgency than #1 since registrations are a one-time-per-member event and this server appears to gate registration once per member, but still fully unbounded. Suggested direction: same as above — SQL-side filtering plus pagination, or at least a sane cap with a "show more" affordance once submission counts run into the thousands.
3. **Low impact, by design:** `GET /birthdays` (`src/web/routes/birthdays.ts:24`) returns all birthdays unbounded, but `idx_birthdays_user` is a unique index on `user_id` — this table is capped at one row per guild member by construction, so it can never exceed guild size. No action needed.
4. **Low impact:** `GET /events/attendance/months` (`src/web/routes/eventAttendance.ts:296-309`) calls `listEventStartTimes()` — `SELECT starts_at FROM apollo_events` with no filter/limit — to build the month-picker's per-month event counts. This grows with total event count over the bot's lifetime (documented in the repository function's own comment as "not paginated"). At realistic scale (a few events/week over a few years is still only low thousands of rows, each just one TEXT column) this is a non-issue for years; flagging only because it's the other genuinely-unbounded read in the event-attendance path. **Theoretical for now, worth revisiting only if event volume becomes very high** (e.g. multiple events per day for a decade).

## Frontend rendering

1. **Theoretical, low real-world impact:** `web/src/components/SignupRow.tsx:76` rebuilds `members.map((m) => ({...}))` inline on every render for every row that still needs manual linking (`needsLink`), rather than memoizing the mapped options array once at the parent level (`EventAttendanceDetail.tsx`) and passing it down. For a guild with a few hundred members and at most a handful of unresolved signups per event, this is cheap today, but it re-does the same O(members) transform once per unresolved row on every parent re-render (e.g. after linking any other row triggers a full `setEvent(updated)`). Fix direction: compute `members.map(...)` once with `useMemo` in `EventAttendanceDetail.tsx` and pass the derived options array down instead of raw `members`.
2. **Low impact:** Neither `MemberAudit.tsx` nor `EventAttendanceDetail.tsx`/`EventAttendance.tsx` virtualize their result tables, but every list is already capped server-side (500/500/200 respectively) or bounded by realistic per-event attendee counts, so this is not a real problem at this bot's scale. Not worth adding a virtualization library for.
3. **No polling anywhere in the app** — every data fetch is triggered by mount, a debounced search input, or an explicit user action (checked across all of `web/src/pages/**` and `web/src/components/**`). No `setInterval`/refetch-on-focus pattern exists to flag.
4. **No bundle-size concerns.** `web/package.json` has a minimal dependency set (React, react-dom, react-router-dom only); no heavy chart/date/UI libraries were found anywhere in `web/src/**`. `ReactionRoles.tsx` (863 lines) is a single large component, but it's config-editing UI whose data volume (panels/mappings) is bounded by what an admin manually creates, not by guild size — it doesn't scale with member count, message history, or event count, so it's out of scope for a scaling audit despite its line count.

## Storage / disk growth

Ranked by growth rate and how soon it's likely to matter for a long-running single-guild bot:

1. **Highest growth risk, no pruning: `member_records`.** One row per distinct user ever observed by the bot (join, leave, or registration), upserted by `user_id` — never deleted, by design (the Member Audit page's whole purpose is to show full history). This is the table backing findings #1/#2 above. Growth rate is roughly proportional to cumulative distinct members who have ever joined/registered, which for an active community accumulates for the life of the bot with no cap. This is a legitimate retention-policy gap, not just a query-shape problem: even with perfectly optimized SQL-side filtering, the table itself grows forever. Suggested direction (product decision, not just code): either accept unbounded growth (SQLite handles tens of thousands of rows fine, so this may never be a *disk* problem) but at least stop loading the whole table into memory per request (see findings above), or introduce an explicit archival/retention policy for members who left N years ago if disk/privacy considerations warrant it.
2. **Medium growth risk, no pruning: `apollo_event_voice_log`.** Append-only join/leave/present-at-start/present-at-end log, one row per voice-channel state transition per user per event (`src/db/eventAttendanceRepository.ts:605-612`, `appendVoiceLog`). Only ever cleared via `ON DELETE CASCADE` when an admin manually deletes an event from the dashboard (`DELETE /events/attendance/:id`) — there is no automatic retention. Rough growth estimate: an event with ~15 tracked attendees and minimal reconnects generates on the order of 30-60 rows; at "a couple of events per week," that's roughly 3,000-6,000 rows/year. SQLite handles this volume trivially for years; this is a "theoretical, low real-world impact for this bot's scale" finding unless event cadence or attendee counts are much higher than assumed, or the bot runs for a decade-plus. Also true of `apollo_event_signups` (smaller row count, same lifecycle).
3. **Low risk, already handled: `web_sessions`.** `sweepExpiredSessions()` (`src/db/sessionsRepository.ts:66-68`) runs once at startup (`src/web/server.ts:36`), and `getSession()` additionally deletes a row lazily the moment it's read past expiry (`src/db/sessionsRepository.ts:51-59`). The only accumulation scenario is an abandoned session (cookie never returns) sitting in the table until the next process restart — for a small admin-only dashboard with a handful of logins, this is negligible. No periodic in-process sweep exists (only startup), but given how few sessions a single-guild admin dashboard ever creates, this is **theoretical, not worth adding a cron for**.
4. **No issue: `birthdays`, `reaction_role_panels`/`reaction_role_mappings`, `settings`, `command_settings`, `birthday_anchor_messages`.** All are naturally capped — one row per guild member (unique index enforced), or per admin-created config object. None grow with message/event volume.

## Fastify/Node-side performance

1. **No blocking I/O in request handlers.** better-sqlite3 is synchronous but in-process and fast; no filesystem reads/writes were found inside any `src/web/routes/**` handler. WAL mode is enabled (`src/db/index.ts:26`), which is the right call for a server that's both reading (dashboard) and writing (Discord event handlers) concurrently.
2. **No caching gaps worth flagging.** This is a low-traffic, admin-only dashboard (single guild, handful of concurrent staff users at most) — repeated identical work per request (e.g. `getCachedMembers()` lookups, `getSettings()` reads) is already served from in-memory caches maintained elsewhere in the bot, not re-fetched from Discord or re-queried per dashboard request. Adding a response cache layer here would be solving a problem this traffic profile doesn't have.
3. **`normalizeForSearch()` (`src/services/memberSearch.ts:26-36`) does non-trivial work (regex-based Unicode fancy-character unmapping, `transliteration` library call, NFKD normalization, more regex) per candidate name, per request, with no memoization** — and it's invoked from both the member-audit and registrations routes over their full unbounded result sets (see Unbounded payloads #1/#2). At today's guild size this is milliseconds; it compounds with the unbounded-table findings above rather than being a standalone issue. If those tables' reads get pushed into SQL/paginated, this stops mattering; if they don't, this is what makes each of those unpruned rows cost more than a plain string compare would.

## Priority ranking (top items to act on if/when it matters)

1. `GET /members/audit` and `GET /members/registrations` loading their entire un-pruned tables into memory per request (Unbounded payloads #1, #2) — the only two findings that get strictly worse every month the bot runs, with no ceiling.
2. `EventAttendanceDetail.tsx` pulling the full member-audit endpoint just for a linking dropdown (Unbounded payloads #1) — an easy, low-risk win: a dedicated in-guild-only members endpoint would cut that page's load cost independent of any left-member retention policy decision.
3. Everything else in this report (`SignupRow` memoization, session sweep cadence, `apollo_event_voice_log` growth, missing `register_status` index) is either already handled adequately or firmly in "won't matter for years at this bot's scale" territory.
