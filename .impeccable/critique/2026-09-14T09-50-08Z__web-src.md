## Design Specificity Verdict

**LLM assessment**: Grounded, not category-interchangeable. `theme.css` pulls Discord's actual client hex values verbatim; the message-preview and event-embed mockups are pixel-accurate reproductions of what a member will see, deliberately breaking the app's own type scale to match Discord's real client sizes instead. Vocabulary (Zugesagt/Abgesagt/Vielleicht, Mindest-Berechtigungsstufe, Anwesenheits-Sprachkanal) is Discord-domain-specific throughout, and the registration confirm dialog names the exact Discord-side effect before committing. This could not be repainted as a generic SaaS panel unchanged.

**Deterministic scan**: CLI detector (`detect.mjs` on `web/src`) returned exit 0 / zero findings — but only because `.impeccable/config.json` already carries 10 documented suppressions matching DESIGN.md's stated exceptions (the message-preview signature component's Discord-mirrored pixel sizes and colors, scrim overlays, etc.). That's the suppression list doing its job, not evidence of a clean slate.

Live browser-injected overlay evidence (5/5 pages tested) surfaced findings **outside** the suppressed set:
- `/`: `all-caps-body` (31 chars uppercase body text — possibly the documented "Meta" type role, unconfirmed), `overused-font` (Roboto, 100%)
- `/reaction-roles`: `body-text-viewport-edge` (a 50-char paragraph bleeding to the viewport edge)
- `/birthdays`: `overused-font` (94%)
- `/events`: `line-length` (~110 chars/line, target <80), `overused-font` (100%)
- `/settings`: `overused-font` (100%)

**False-positive flag**: every `overused-font` hit is almost certainly a systematic false positive here — DESIGN.md explicitly mandates a single system-font stack everywhere ("an admin tool... has no reason to load or pair a custom typeface"), so the detector's generic "you're only using one font" heuristic runs directly against this project's deliberate, documented choice. Treat all five as non-issues.

The `line-length` finding on `/events` and the `body-text-viewport-edge` finding on `/reaction-roles` are **not** false positives — DESIGN.md caps hint prose at 60ch but the running body copy on these two pages isn't held to that same measure.

## Overall Impression

The system is doing exactly what it set out to do — "Same Client, Different Door" is real, not aspirational, and it shows in the small decisions (message previews, terminology, confirm-dialog copy) as much as the big ones (the color palette). The biggest opportunity isn't visual; it's that the one accent color used for links and focus rings fails contrast, and the one interaction pattern meant to slow admins down at high-stakes moments (the confirm dialog) doesn't visually distinguish "confirm" from "cancel" on its most common, non-destructive path.

## What's Working

1. **Stakes-matched confirmation friction** — destructive actions require typing the exact name; low-stakes actions get a lighter dialog. Most admin tools get this uniformly wrong in one direction.
2. **`MemberOverview` as a cross-cutting profile** — pulls birthday/registration/event-attendance history for one person into one page, eliminating tab-hopping across three otherwise-separate pages.
3. **Functional, not decorative, Discord mockups** — the event-embed and reaction-role previews are pixel-accurate, which matters for a non-technical moderator who needs to trust "this is what members will see" before publishing.

## Priority Issues

**[P1] Accent color fails WCAG contrast as link/border text**
Why it matters: `--accent: #5865f2` is used directly as link color and focus-ring/border color on the `#313338` background — measured contrast is 2.74:1, failing AA's 4.5:1 (text) and 3:1 (non-text) minimums. It's the color on every member-name link, "Thread öffnen," and back-link in the app.
Fix: introduce a lighter link-specific token (e.g. ~#7c86ff) for text/border use on dark surfaces; keep --accent as-is for buttons, where white-on-accent already passes at 4.61:1.
Suggested command: /impeccable colorize (or /impeccable audit for a full contrast sweep)

**[P2] Confirm dialog's affirmative button has no visual priority on its common path**
Why it matters: in `ConfirmContext.tsx`, the confirm button only gets `.danger` styling when `isDanger`; otherwise it's an unstyled button visually identical to "Abbrechen." Verified live: approving a registration (granting server access) shows two indistinguishable gray buttons.
Fix: add `.primary` styling to the affirmative button when `!isDanger`.
Suggested command: /impeccable polish

**[P2] Commands page breaks on mobile**
Why it matters: below 700px, the permission column's two `<select>` elements get squeezed by `BaseTable`'s generic stacking, truncating "Mindest-Berechtigungsstufe" to "Mindest-Be" with no ellipsis — reproduced live at 500px.
Fix: give the permission cell its own stacked mobile layout instead of relying on the generic single-value pattern.
Suggested command: /impeccable adapt

**[P2] No bulk actions anywhere**
Why it matters: approving 5 pending registrations or re-tiering 10 commands after a policy change is 5–10 separate one-row round trips (confirmed: Commands.tsx has no multi-select state). This is the one heuristic score (Flexibility and Efficiency, 2/4) that's a real gap for a returning-admin tool.
Fix: multi-select + bulk "set minimum tier to..." on Commands; bulk approve/reject on the Registrierungen table.
Suggested command: /impeccable optimize (workflow efficiency) or /impeccable shape (design the bulk-action UX first)

**[P3] Running body copy isn't held to a consistent measure**
Why it matters: /events runs ~110 characters per line (detector-confirmed) and /reaction-roles has a paragraph bleeding to the viewport edge — both violate the 60ch cap DESIGN.md already establishes for hint prose, just not enforced outside that one context.
Fix: apply the existing .muted.small-style max-width constraint to running body copy generally, not just hint paragraphs.
Suggested command: /impeccable layout

## Persona Red Flags

**Alex (Power User)**: No bulk approve/reject on Registrierungen, no bulk permission-tier change on Commands — every action is a single row, single save.

**Sam (Accessibility-Dependent)**: Accent-on-dark contrast fails AA (2.74:1, quantified above); danger badge/button text also measured under 4.5:1 (~3.2–3.35:1) against its own tinted background. Keyboard focus was visible where spot-checked, but not exhaustively verified across every interactive component.

**Casey (Mobile)**: Commands' permission column truncates unreadably below 700px (reproduced) — but Member Audit/Registrierungen correctly uses the app's card-stacking pattern and is genuinely good on mobile, so this is a Commands-specific gap, not a systemic one.

## Minor Observations

- Event detail's "Keine Rückmeldung: 2" tally doesn't show who those two people are without cross-referencing the full member list.
- Registration approval requires "Thread öffnen" to read the applicant's answers in Discord, then returning to click "Genehmigen" — a real context switch with nothing inline to reference.
- `.stat-tile .value`'s overflow-wrap: break-word breaks strings like "MockBot#0000" mid-digit even at normal desktop width.
- Commands page has no search/filter/grouping — fine at ~10 rows today, won't scale.
- The all-caps-body detector hit on `/` is a probable false positive (likely the documented "Meta" type role) but wasn't confirmed against the exact flagged element.
